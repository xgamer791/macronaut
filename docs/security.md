# Security review

Written while moving the app from Supabase-plus-local-SQLite to Convex.
Section 1 is what this change fixes, section 2 is what is still open, with the
reasoning for each.

## 1. Fixed

### Every account shared a device, and every device held the data

Before this change each account's diary lived in a local SQLite / IndexedDB
database on the device, isolated from other accounts by a scope resolved in
the client. That worked, but it meant the client was the only thing between
one account's rows and another's, and it meant a recovered device carried the
diaries of everyone who had signed in on it.

Data now lives in the account on Convex. The device holds nothing but the
session tokens. Two accounts on one device cannot see each other's rows
because the server will not return them — the client has no say in it.

### Isolation is enforced where the data is

Every function in `convex/` starts with `requireUserId(ctx)`, which reads the
user from the verified JWT and throws `Not signed in` without one. Every table
carries `userId`; every read goes through an index whose first field is
`userId`; every write to an existing row loads it and refuses it unless the
owner matches (`requireOwned`). The client never passes a user id.

The rule to keep: the client never filters by user for security. The server
refuses the rows either way. `tests/convex/isolation.test.ts` fails if a
function ever returns or modifies another account's row, or answers without a
session.

### Secrets left the bundle

The app is a static site and a mobile binary; anything compiled into it is
public. The previous design accepted that for the Supabase publishable key
(protected by Row Level Security), and the deploy workflow refused privileged
keys. Now nothing sensitive is in the bundle at all:

| Secret | Lives | Reaches the bundle? |
|---|---|---|
| Google OAuth client secret | Convex deployment env (`AUTH_GOOGLE_SECRET`) | No — the OAuth exchange runs on the Convex site URL |
| Resend API key | Convex deployment env (`AUTH_RESEND_KEY`) | No — codes are sent from a Convex action |
| Shared xAI key for AI food scan | Convex deployment env (`XAI_API_KEY`) | No — a Convex action calls xAI; the client never sees the key |
| Session signing key | Convex deployment env (`JWT_PRIVATE_KEY`, `JWKS`) | No — generated by `scripts/convex-auth-keys.mjs` and stored directly |
| Convex deploy key | GitHub Actions secret (`CONVEX_DEPLOY_KEY`) | No — read only by the deploy step |
| Convex deployment URL | `EXPO_PUBLIC_CONVEX_URL` | Yes — it is the address clients connect to, public by design |

### OAuth redirects are allow-listed

`convex/auth.ts` accepts a `redirectTo` only for the deployed site
(`SITE_URL`), the app's own `macronaut://` scheme, Expo Go, and
`http://localhost:*`. Anything else throws. Convex Auth's code flow uses PKCE,
so even a redirect to an attacker's site would deliver a code that cannot be
exchanged without the verifier held by the client that started the flow — but
there is no reason to hand one out.

### Email codes are the whole credential, so they are treated as one

Six digits from the platform CSPRNG with unbiased sampling, ten-minute
expiry, hashed at rest by Convex Auth, and a failed-attempt limit per account.
Sending a code does not reveal whether the address already has an account.

### Accounts can be deleted from the app

Both stores require it. Settings → Account → **Delete account** erases every
row the account owns, then its sessions, refresh tokens, linked sign-in
methods and verification codes, and finally the user record. It runs in
bounded batches; the app repeats until the server reports done.

### Smaller items

- Session tokens are stored in `expo-secure-store` on native, chunked because
  SecureStore rejects values over 2048 bytes and a half-written value reads
  back as absent rather than as a truncated token.
- Provider metadata (`name` from Google) is user-controlled text. It is capped
  at 60 characters on the server and again where it is shown.
- Raw provider error strings are not rendered. `friendlyAuthError` maps them
  to messages that say what to do next.
- `undefined` never reaches a Convex argument: the repositories strip it
  (`clean`), because Convex rejects it and the app builds objects with
  optional fields left undefined.
- The deploy workflow fails, before publishing, if the exported bundle does
  not contain a Convex deployment URL — a config that never reached the
  bundler would otherwise ship an app that cannot sign in.

## 2. Open

Ordered by how much they matter.

### Third-party API credentials are published in the bundle

`src/services/food/fatsecret.ts` reads `EXPO_PUBLIC_FATSECRET_CLIENT_ID` and
`EXPO_PUBLIC_FATSECRET_CLIENT_SECRET` and sends them as an HTTP Basic
`client_credentials` grant. An OAuth2 client secret in a public client is a
leaked credential by construction. `EXPO_PUBLIC_NUTRITIONIX_APP_KEY` has the
same problem. The USDA key is lower stakes — it only gates a rate limit.

The fix is now straightforward: a Convex action holding the keys and
forwarding search and barcode requests, after which the client needs no
provider credentials at all. Until then, treat any configured FatSecret or
Nutritionix credential as public and scope it to nothing else.

### Shared xAI key for AI food scan

AI food scan's key is `XAI_API_KEY` on the Convex deployment. A public query
only returns `{ allowed }`; the action reads the env var, calls xAI, and
returns the food estimate. Putting that key in a Convex table would show it
in the data browser, backups, and any query that listed the row — worse
than a server env var for a shared secret.

The voice assistant that stored a personal key as `grokApiKey` has been
removed. Leftover `grokApiKey` / `assistantMemory` settings rows are unused.

### App Store requirement

iOS requires Sign in with Apple wherever a third-party social login is
offered. Google sign-in ships here without it, which will fail review. Convex
Auth supports Apple as an OAuth provider; add it before submitting.

### Web sessions are reachable from script

A static host cannot set `httpOnly` cookies, so on web the session lives in
`localStorage` and a successful XSS could steal it. What keeps that acceptable
is that the app loads no third-party scripts and renders no raw HTML — worth
re-checking before adding either. JWTs live one hour and are reused when the
app reopens; refresh tokens rotate on use and are invalidated on reuse.

### No MFA

Convex Auth has no built-in second factor. Email-code sign-in is single
factor by definition; Google sign-in inherits whatever the Google account
enforces.

### Email delivery depends on a verified domain

`AUTH_EMAIL_FROM` must be on a domain verified in Resend. Until it is, the
`onboarding@resend.dev` sender only delivers to the Resend account owner, so
nobody else can sign in with a code; the login screen reports this as "Email
sign-in isn't available yet" rather than blaming the address. Verify the
domain before real users arrive.

### Deletion is best-effort against concurrent writes

`deleteAccount` runs as a mutation, so it is atomic per batch, but a client
that keeps writing while deletion is in progress could leave rows behind.
The app signs out immediately after; a background job that sweeps rows whose
`userId` no longer exists would close the gap.

## Verifying isolation

The regression that matters most is covered by `tests/convex/isolation.test.ts`
on every push, and should still be checked through a real browser after any
change to auth or the data layer:

1. Sign in as A, log a diary entry.
2. Sign out, sign in as B. B's diary must be empty.
3. Sign out, sign back in as A. A's entry must be there.
